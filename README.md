# مدار — سامانه‌ی یکپارچه‌ی مدیریت عملیات

مدار یک سامانه‌ی عملیات کسب‌وکار برای مدیریت سایت‌ها و مزارع، تولید، سفارش، شرکا و تأمین‌کنندگان، انبار، ارسال، کیفیت، امور مالی، اهداف و تاریخچه‌ی تغییرات است. سامانه به یک صنعت یا محصول خاص محدود نیست.

## ورود و فضای کاری

رابط فارسی و راست‌چین به API سمت سرور متصل است. ورود و ثبت‌نام در نسخه‌ی فعلی فقط با نام کاربری و رمز عبور انجام می‌شود؛ شماره موبایل، ایمیل و تأیید پیامکی الزامی نیستند. ثبت‌نام مستقل یک فضای کاری تازه و عضویت مالک می‌سازد. برای پیوستن به فضای کاری دیگر باید از دعوت معتبر همان شرکت استفاده شود.

دسترسی‌های واقعی از عضویت و نقش تاییدشده‌ی سمت سرور می‌آیند؛ یک انتخابگر نقش یا تغییر شناسه در مرورگر راهی برای اعطای دسترسی نیست. نقش‌های مشتری، تأمین‌کننده و راننده باید فقط رکوردهای مرتبط با خودشان را ببینند.

## ظاهر و تجربه کاربری

حالت روشن و تاریک برای دموی عمومی، صفحه ورود/ثبت‌نام و فضای کاری عملیاتی از یک تنظیم مشترک استفاده می‌کند. انتخاب کاربر در `localStorage` با کلید `simorgh-theme` حفظ می‌شود و در نسخه‌های بومی Capacitor، رنگ نوار وضعیت نیز همگام می‌شود. رابط باید در تمام حالت‌ها فارسی، راست‌چین و با فونت Vazirmatn باقی بماند؛ انیمیشن‌ها از تنظیم سیستمی `prefers-reduced-motion` پیروی می‌کنند.

## دموی معرفی بدون ورود

نسخه‌ی نمایشی عمومی در `https://medar-api.dengxiao445.workers.dev` در مسیرهای `/` و `/demo` یک فضای کاری تعاملیِ فقط‌خواندنی باز می‌کند. سفارش‌ها، اعداد و نام‌های نمایش‌داده‌شده داده‌ی نمونه‌اند و باید با برچسب «داده نمونه» دیده شوند. این میزبان فقط `GET /api/health` را برای نمایش سلامت واقعی سرویس و یک پاسخ ناشناس برای `GET /api/auth/me` می‌پذیرد؛ ثبت‌نام، ورود، خواندن/نوشتن داده‌های کسب‌وکار و فایل‌ها در لایه‌ی API نیز با HTTP 403 بسته می‌شوند، حتی اگر کسی مستقیماً API را صدا بزند.

محیط عملیاتی در `https://medar-ops.dengxiao445.workers.dev` قرار دارد و برای استفاده‌ی واقعی، نشست معتبر لازم دارد. شناسه‌ی حالت Worker با متغیر سروری `MEDAR_MODE` تنظیم می‌شود: `public-demo` پیش‌فرضِ fail-closed است؛ فقط استقرار عملیاتی مجاز است صریحاً `MEDAR_MODE=operational` داشته باشد. متغیر `VITE_ENABLE_AUTH_UI` فقط انتخاب رابط کاربری بیلد است و به‌تنهایی هیچ مجوزی اعطا نمی‌کند.

## معماری

`React/Vite SPA → Cloudflare Worker API → Neon PostgreSQL`

- API و نشست‌ها در `worker/index.ts`
- کلاینت HTTP در `src/lib/apiClient.ts`
- سازگاری داده‌ی جدول/RPC و فضای فایل در `src/lib/dataClient.ts`
- migrationهای مخصوص Worker/Neon در `worker/migrations/`
- workflow انتشار دستی در `.github/workflows/cloudflare-worker.yml`

پوشه‌ی `supabase/migrations/` به‌عنوان تاریخچه‌ی schema قبلی نگه‌داری شده است؛ برای انتقال داده یا اجرای SQL، فایل‌ها باید جداگانه بازبینی و به schema هدف تطبیق داده شوند. کل migrationهای تاریخی را یکجا روی Neon اجرا نکن.

## راه‌اندازی محلی

Node.js 22 یا بالاتر توصیه می‌شود.

```bash
npm install
npm run dev
npm run typecheck
npm run lint
npm run test
npm run build
npm run test:e2e
```

Worker به `DATABASE_URL` در محیط سرور نیاز دارد. مقدار اتصال دیتابیس و Cloudflare token نباید در `VITE_*` یا کد client قرار گیرد. برای Worker محلی از secretهای محیط توسعه استفاده کن، نه secretهای Production.

## وضعیت انتشار و آزمون

شاخه‌ی فعلی مهاجرت `migration/cloudflare-neon-foundation` است: [PR #25](https://github.com/Ehsanamn1/simorgh/pull/25). CI، ساخت Worker، تست‌های مرورگر، خروجی debug اندروید و بسته‌ی شبیه‌ساز iOS باید برای آخرین commit بررسی شوند.

Workflow انتشار پس از ادغام روی `main` اجرا می‌شود و secrets امن `MEDAR_DATABASE_URL`, `CLOUDFLARE_API_TOKEN` و `CLOUDFLARE_ACCOUNT_ID` می‌خواهد. انتشار Worker در ۱۷ اکتبر ۲۰۲۶ با موفقیت انجام شد و `/api/health` اتصال Neon را تأیید کرد. تلاش اول به‌علت غیرفعال‌بودن R2 (خطای 10042) متوقف شده بود؛ سپس انتشار اصلی بدون binding فایل موفق شد. برای اینکه API اصلی بتواند منتشر شود، binding مربوط به R2 موقتاً از Worker حذف شده است؛ endpointهای فایل در این وضعیت HTTP 503 می‌دهند. پس از فعال‌کردن R2 باید binding برگردد و بارگذاری/خواندن فایل خصوصی smoke-test شود. موفقیت Production فقط با سبزشدن workflow و آزمون زنده‌ی `/api/health` تأیید می‌شود.

شاخه‌ی جداگانه‌ی Neon که بررسی شده، فعلاً فاقد حساب، شرکت، عضویت و سفارش واقعی است. انتقال داده از دیتابیس قبلی هنوز انجام نشده؛ قبل از انتقال، backup قابل‌بازیابی، تطبیق تعداد رکوردها و برنامه‌ی rollback الزامی است.

## محدودیت‌های شناخته‌شده

- صف نوشتن آفلاین و حل تعارض هنوز کامل نیست.
- مسیر تجاری سفارش تا موجودی، تولید، تحویل، فاکتور و تسویه باید با تست پذیرش end-to-end و حساب‌های مجزای نقش‌محور اثبات شود.
- Android debug برای تست داخلی است؛ انتشار فروشگاهی به امضای انتشار نیاز دارد. خروجی iOS فعلی شبیه‌ساز است و اپ دستگاه واقعی محسوب نمی‌شود.
- هیچ داده‌ی نمونه‌ی ساختگی، حساب مدیر پنهان یا گذرواژه‌ی پیش‌فرضی نباید وارد محیط واقعی شود.
