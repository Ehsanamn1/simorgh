# مدار — سامانه‌ی یکپارچه‌ی مدیریت عملیات

مدار یک سامانه‌ی عملیات کسب‌وکار برای مدیریت سایت‌ها و مزارع، تولید، سفارش، شرکا و تأمین‌کنندگان، انبار، ارسال، کیفیت، امور مالی، اهداف و تاریخچه‌ی تغییرات است. سامانه به یک صنعت یا محصول خاص محدود نیست.

## ورود و فضای کاری

رابط فارسی و راست‌چین به API سمت سرور متصل است. ورود عملیاتی با نام کاربری و رمز عبور انجام می‌شود؛ شماره موبایل، ایمیل و تأیید پیامکی الزامی نیستند. ثبت‌نام عمومی در محیط عملیاتی و ثبت‌نام با کد دعوت غیرفعال است؛ کاربر جدید را فقط مالک/مدیر مجاز مجموعه از بخش «دسترسی کاربران» ایجاد می‌کند. نقش‌های قابل ایجاد در نسخه عملیاتی مدیر، کارشناس، تأمین‌کننده و راننده‌اند.

**مرز محصول:** مدار پنل عملیات و شبکهٔ تأمین است، نه درگاه ثبت‌نام مشتری و سفارش‌گیری عمومی. کاتالوگ خرید و صفحات سفارش/حساب مشتری از ناوبری عملیاتی حذف شده‌اند و مسیرهای قدیمی آن‌ها به صفحهٔ اصلی امن برمی‌گردند. API نیز ساخت حساب مشتری و ارسال/لغو سفارش توسط نقش مشتری را رد می‌کند. عضویت‌ها و رکوردهای قدیمی مشتری فقط برای سازگاری و خواندنِ محدود باقی می‌مانند؛ هیچ دادهٔ قدیمی به‌خاطر این تغییر حذف نمی‌شود. سفارش‌های داخلی مجموعه که توسط کاربران مجاز اداره می‌شوند حفظ شده‌اند.

دسترسی واقعی از عضویت و نقش تأییدشده‌ی سمت سرور می‌آید؛ انتخابگر نقش یا تغییر شناسه در مرورگر مجوز تازه‌ای اعطا نمی‌کند. تأمین‌کننده و راننده فقط داده‌ها و گردش‌های کاری مرتبط با عضویت تأییدشده‌شان را می‌بینند.

## ظاهر و تجربه کاربری

حالت روشن و تاریک برای دموی عمومی، صفحه ورود/ثبت‌نام و فضای کاری عملیاتی از یک تنظیم مشترک استفاده می‌کند. انتخاب کاربر در `localStorage` با کلید `simorgh-theme` حفظ می‌شود و در نسخه‌های بومی Capacitor، رنگ نوار وضعیت نیز همگام می‌شود. رابط باید در تمام حالت‌ها فارسی، راست‌چین و با فونت Vazirmatn باقی بماند؛ انیمیشن‌ها از تنظیم سیستمی `prefers-reduced-motion` پیروی می‌کنند.

## دموی معرفی بدون ورود

نسخه‌ی نمایشی عمومی در `https://medar-api.dengxiao445.workers.dev` در مسیرهای `/` و `/demo` یک فضای کاری تعاملیِ فقط‌خواندنی باز می‌کند. سفارش‌ها، اعداد و نام‌های نمایش‌داده‌شده داده‌ی نمونه‌اند و باید با برچسب «داده نمونه» دیده شوند. این میزبان فقط `GET /api/health` را برای نمایش سلامت واقعی سرویس و یک پاسخ ناشناس برای `GET /api/auth/me` می‌پذیرد؛ ثبت‌نام، ورود، خواندن/نوشتن داده‌های کسب‌وکار و فایل‌ها در لایه‌ی API نیز با HTTP 403 بسته می‌شوند، حتی اگر کسی مستقیماً API را صدا بزند.

محیط عملیاتی در `https://medar-ops.dengxiao445.workers.dev` قرار دارد و برای خواندن/تغییر داده‌های واقعی، نشست معتبر و عضویت سمت سرور لازم دارد. Worker عملیاتی با فایل تنظیمات اختصاصی `worker/wrangler-medar-ops.toml` و متغیر `MEDAR_DEPLOYMENT_MODE=operational` منتشر می‌شود؛ پیکربندی bootstrap نیز جداست و مجوز عملیات ندارد. محیط نمایشی `medar-api` با `MEDAR_MODE=public-demo` فقط‌خواندنی است. مقدار صریح `MEDAR_DEPLOYMENT_MODE` بر متغیر سازگاری قدیمی اولویت دارد تا حالت نمایشی به‌اشتباه روی Worker عملیاتی اعمال نشود. `VITE_ENABLE_AUTH_UI` فقط رابط کاربری بیلد را انتخاب می‌کند و به‌تنهایی هیچ مجوزی اعطا نمی‌کند.

## معماری

`React/Vite SPA / Capacitor mobile app → same authenticated Cloudflare Worker → same Neon PostgreSQL`

مدار محصول عملیاتی شاخص برند **راز صحرا (Raz-e Sahra)** است. سایت شرکتی و CMS راز صحرا در مخزن مستقل `Ehsanamn1/razsahra` استقرار می‌یابد؛ نسخه وب مدار از مسیر `/madar/` و پراکسی هم‌مبدأ `/api/medar/api/...` قابل دسترسی است. این اتصال، دیتابیس CMS و دیتابیس عملیاتی مدار را ادغام نمی‌کند و SSO ساختگی یا اشتراک token در مرورگر ایجاد نمی‌کند. راهنمای مسیر فعلی در [استقرار راز صحرا](docs/DEPLOYMENT_RAZ_SAHRA.md) ثبت شده است.

- وب و Android/iOS یک codebase و قرارداد runtime مشترک در `src/lib/runtimeConfig.ts` دارند. API عملیاتی با `MEDAR_OPS_API_BASE_URL` در workflow موبایل تنظیم می‌شود؛ داده‌ها بین دستگاه‌ها از سرور واحد همگام می‌شوند، نه از local storage دستگاه.
- پس از ورود، کلاینت‌ها heartbeat کم‌حساسیت ارسال می‌کنند. پنل مالک/مدیر در «مرکز فرمان شبکه» سلامت زنده‌ی API/دیتابیس و آخرین فعالیت کلاینت‌های وب و موبایل را از `GET /api/admin/system/clients` می‌خواند. داده‌ی قدیمی با برچسب آخرین فعالیت نشان داده می‌شود و آنلاین بودن صرفاً یعنی heartbeat در سه دقیقه‌ی اخیر.
- migration `0012_client_presence.sql` جدول حضور کلاینت‌ها را اضافه می‌کند؛ این جدول فقط مانیتورینگ است و منبع احراز هویت یا مجوز نقش نیست.

- API و نشست‌ها در `worker/index.ts`
- کلاینت HTTP در `src/lib/apiClient.ts`
- سازگاری داده‌ی جدول/RPC و فضای فایل در `src/lib/dataClient.ts`
- migrationهای مخصوص Worker/Neon در `worker/migrations/`
- workflow انتشار دستی در `.github/workflows/cloudflare-worker.yml`

پوشه‌ی `supabase/migrations/` به‌عنوان تاریخچه‌ی schema قبلی نگه‌داری شده است؛ برای انتقال داده یا اجرای SQL، فایل‌ها باید جداگانه بازبینی و به schema هدف تطبیق داده شوند. کل migrationهای تاریخی را یکجا روی Neon اجرا نکن.

## توسعهٔ بدون دیتابیس و انتقال به هاست

راهنمای حالت استاتیک، توسعه بدون دیتابیس عملیاتی، محدودیت‌های فعلی بک‌اند و چک‌لیست انتقال امن به هاست: [راهنمای توسعه و مهاجرت](docs/LOCAL_DEVELOPMENT_AND_HOST_MIGRATION.md).

## راه‌اندازی محلی

Node.js 22 یا بالاتر توصیه می‌شود.

```bash
npm install
npm run dev
npm run typecheck
npm run lint
npm run test
npm run build
npm run test:e2e
```

Worker به `DATABASE_URL` در محیط سرور نیاز دارد. مقدار اتصال دیتابیس و Cloudflare token نباید در `VITE_*` یا کد client قرار گیرد. برای Worker محلی از secretهای محیط توسعه استفاده کن، نه secretهای Production.

## وضعیت انتشار و آزمون

نسخهٔ عملیاتی بررسی‌شده در `main`: `70329106d6cd921e1c036714157986b72e0ea201`. [CI اصلی](https://github.com/Ehsanamn1/simorgh/actions/runs/39653283320)، [انتشار Worker و آزمون زنده](https://github.com/Ehsanamn1/simorgh/actions/runs/39653283449)، [ساخت Android](https://github.com/Ehsanamn1/simorgh/actions/runs/39653283373) و [ساخت iOS](https://github.com/Ehsanamn1/simorgh/actions/runs/39653283318) موفق بوده‌اند؛ برای پذیرش تجاری، محدودیت‌ها و گیت‌های باز را در [Commercial Pilot Readiness](./docs/COMMERCIAL_PILOT_READINESS.md) دنبال کنید.

Workflow انتشار پس از ادغام روی `main` اجرا می‌شود و secrets امن `MEDAR_DATABASE_URL`, `CLOUDFLARE_API_TOKEN` و `CLOUDFLARE_ACCOUNT_ID` می‌خواهد. آخرین انتشار عملیاتی [run 39653283449](https://github.com/Ehsanamn1/simorgh/actions/runs/39653283449) موفق بود و سلامت Worker، اتصال Neon، محدودیت ثبت‌نام عمومی، کنترل دسترسی بدون نشست، حفاظت origin/CORS، ورود دسکتاپ/موبایل و هدایت دمو به محیط عملیاتی را تأیید کرد. در صورت نبودن binding مربوط به R2، کد فعلی برای فایل‌های خصوصی fallback دیتابیس با سقف ۱۰ مگابایت برای هر فایل دارد؛ پس حذف R2 به‌تنهایی به معنی HTTP 503 برای همهٔ endpointهای فایل نیست. بااین‌حال، آپلود، بازیابی مجاز/غیرمجاز و حذف فایل در endpoint زنده هنوز در پذیرش نهایی مالک آزموده نشده‌اند؛ این مسیر را تا ثبت شواهد واقعی، قابلیت تأییدشدهٔ تجاری تلقی نکنید. برای فایل‌های بزرگ‌تر یا بار عملیاتی بیشتر، R2 را فعال و مسیر خصوصی را smoke-test کنید. جزئیات go/no-go در [Commercial Pilot Readiness](./docs/COMMERCIAL_PILOT_READINESS.md) ثبت می‌شود.

شاخه‌ی جداگانه‌ی Neon که بررسی شده، فعلاً فاقد حساب، شرکت، عضویت و سفارش واقعی است. انتقال داده از دیتابیس قبلی هنوز انجام نشده؛ قبل از انتقال، backup قابل‌بازیابی، تطبیق تعداد رکوردها و برنامه‌ی rollback الزامی است.

## محدودیت‌های شناخته‌شده

- صف نوشتن آفلاین و حل تعارض هنوز کامل نیست.
- مسیر تجاری سفارش تا موجودی، تولید، تحویل، فاکتور و تسویه باید با تست پذیرش end-to-end و حساب‌های مجزای نقش‌محور اثبات شود.
- Android debug برای تست داخلی است؛ انتشار فروشگاهی به امضای انتشار نیاز دارد. خروجی iOS فعلی شبیه‌ساز است و اپ دستگاه واقعی محسوب نمی‌شود.
- هیچ داده‌ی نمونه‌ی ساختگی، حساب مدیر پنهان یا گذرواژه‌ی پیش‌فرضی نباید وارد محیط واقعی شود.

راهنماها: [راه‌اندازی امن حساب مالک](docs/OWNER_PROVISIONING.md)، [وضعیت مهاجرت](docs/MIGRATION_STATUS.md)، [تطبیق مراجع رابط کاربری](docs/REFERENCE_BOARD_MAPPING.md) و [ساخت اپ موبایل](docs/MOBILE_APP.md).

## دستیار هوش مصنوعی و واردسازی مخاطبین

- دستیار عملیاتی در همه‌ی پنل‌های واردشده نمایش داده می‌شود. پاسخ‌ها از پرووایدر منتخب (OpenAI، Gemini، DeepSeek یا Anthropic) از مسیر Worker سمت سرور دریافت می‌شوند؛ بدون ثبت API key، پاسخ واقعی تولید نمی‌شود.
- مالک یا مدیر می‌تواند در تنظیمات دستیار مدل و کلید هر پرووایدر را وارد کند. کلید با AES-GCM در سمت Worker رمزنگاری می‌شود و هرگز در پاسخ به مرورگر برگردانده نمی‌شود. برای کلید رمزنگاری پایدار، secret با نام `MEDAR_AI_ENCRYPTION_KEY` را در GitHub Actions تعریف کن تا هنگام انتشار به Worker با نام `AI_ENCRYPTION_KEY` منتقل شود. در غیر این صورت نسخه‌ی فعلی از secret دیتابیس به‌عنوان fallback استفاده می‌کند؛ چرخاندن آن secret بدون ذخیره و انتقال کلید مستقل، دسترسی به کلیدهای AI ذخیره‌شده را از بین می‌برد.
- متن گفتگو و محتوای فایل، هنگام ارسال، برای پرووایدر انتخابی فرستاده می‌شود. لاگ استفاده فقط تعداد نویسه، پرووایدر و زمان را نگه می‌دارد؛ متن گفتگو یا API key در لاگ استفاده ذخیره نمی‌شود.
- دستیار فعلاً می‌تواند شاخص‌های مجاز، کارهای اخیر و ریسک‌ها را تحلیل کند و پیشنهاد برنامه بدهد. خودش عملیات مالی، تغییر سفارش یا پیام به اشخاص را اجرا نمی‌کند. دسترسی متن و داده بر اساس نقش و رکوردهای تخصیص‌یافته محدود شده است.
- ورود مخاطبین از فایل‌های `VCF/CSV/TXT` پشتیبانی می‌کند. ستون `type` در CSV می‌تواند نوع مخاطب را تعیین کند؛ اگر این ستون وجود نداشته باشد، دسته‌ی انتخابی کاربر به‌کار می‌رود. پیش‌نمایش و حذف تکراری‌ها قبل از ذخیره انجام می‌شود.
- مکالمه صوتی نوبتی خودکار نیز اضافه شده است: شروع مکالمه، ارسال خودکار گفتار نهایی، خواندن پاسخ و بازگشت خودکار به گوش‌دادن. این حالت به SpeechRecognition و speechSynthesis مرورگر وابسته است و هنوز صدای تمام‌دوطرفه‌ی بلادرنگ/قابل‌قطع‌کردن در سطح WebRTC را پیاده نمی‌کند.
- دستیار PDF را از مسیر API رسمی برای OpenAI، Gemini و Claude ارسال می‌کند؛ سندهای Office نیز با OpenAI قابل تحلیل‌اند. در این نسخه DeepSeek در مسیر چت، پیوست باینری نمی‌پذیرد؛ برای آن فایل را به متن تبدیل کن یا از پرووایدر سازگار استفاده کن. متن فایل‌های پشتیبانی‌شده مستقیماً خوانده می‌شود.

- در تنظیمات دستیار، دکمه‌ی «تست اتصال بدون ذخیره» کلید و مدل را از مسیر امن Worker آزمایش می‌کند؛ این تست API key جدید را در دیتابیس ذخیره نمی‌کند. فقط پس از موفقیت، دکمه‌ی «ذخیره و فعال‌سازی» را بزن.


## صدای بومی در اپ Android/iOS

- نسخه‌ی بومی از پلاگین‌های سازگار با Capacitor 8 برای تشخیص گفتار و خواندن پاسخ استفاده می‌کند؛ نسخه‌ی مرورگر همچنان از Web Speech API استفاده می‌کند.
- در iOS متن مجوز میکروفون و تشخیص گفتار هنگام تولید پروژه‌ی بومی به `Info.plist` اضافه می‌شود؛ در Android اجازه‌ی میکروفون هنگام شروع اولین نشست صوتی درخواست می‌شود.
- تشخیص گفتار با locale فارسی `fa-IR` اجرا می‌شود. پشتیبانی تشخیص گفتار و صدای فارسی به زبان‌ها/صداهای نصب‌شده روی دستگاه و سرویس گفتار سیستم‌عامل بستگی دارد؛ اگر در دستگاه در دسترس نباشد، ورودی متنی همچنان کار می‌کند.


## میزبانی استاتیک و انتقال به هاست

نسخه عمومی GitHub Pages در حالت استاتیک ساخته می‌شود و در زمان build با `VITE_DISABLE_API_UI=true` هرگونه بررسی اتصال به API را غیرفعال می‌کند. داده‌های داخل این نسخه نمونه و فقط برای نمایش رابط هستند؛ ورود واقعی، چندکاربره بودن و ذخیره‌سازی مشترک در این حالت فعال نیستند.

- انتشار خودکار وب‌سایت: GitHub Pages با workflow فایل `.github/workflows/pages.yml`.
- بسته قابل بارگذاری روی هاست استاتیک: artifact با نام `medar-static-site` در اجرای موفق workflow صفحات؛ ZIP شامل محتوای آماده میزبانی از جمله `index.html`، فایل‌های asset، `404.html` و `.nojekyll` است. محتوای ZIP را در ریشه public_html یا document root هاست استاتیک استخراج کنید.
- بسته سورس کامل: artifact با نام `simorgh-full-project` در workflow منبع؛ برای اجرای محلی به Node.js و `npm install` نیاز دارد و این ZIP به‌تنهایی جایگزین سرور API نیست.
- workflow استقرار Cloudflare به حالت دستی تغییر می‌کند و با هر push به main اجرا نخواهد شد. کد Worker، مهاجرت‌ها و پیکربندی دیتابیس حذف نمی‌شوند؛ این کار از حذف ناخواسته یا از دست رفتن قابلیت‌های آینده جلوگیری می‌کند.

برای فعال کردن عملیات واقعی روی هاست آینده، باید API و ذخیره‌سازی سازگار جداگانه پیاده‌سازی یا میزبانی شوند؛ میزبانی استاتیک به‌تنهایی چنین قابلیتی ندارد.
