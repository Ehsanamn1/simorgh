# استقرار مدار روی دامنه و هاست «راز صحرا»

این راهنما معماری پیشنهادی را برای انتقال امن رابط مدار به دامنهٔ اختصاصی و آماده‌سازی نسخهٔ نصب‌شوندهٔ موبایل مشخص می‌کند. **تا زمانی که نشانی دقیق دامنه، نوع پنل هاست و دسترسی‌های DNS/Cloudflare در اختیار عملیات استقرار قرار نگیرد، اتصال واقعی دامنه انجام‌شده محسوب نمی‌شود.** هیچ گذرواژه یا اطلاعات مالک در این مخزن ذخیره نمی‌شود.

## مسیر پیشنهادی: یک مبدأ برای اپ و API

کم‌ریسک‌ترین انتخاب برای نسخهٔ اول تجاری این است که hostname نهایی، مثلاً `app.<دامنه-راز-صحرا>`، مستقیماً به Worker عملیاتی `medar-ops` متصل شود. همان Worker هم فایل‌های وب‌اپ و هم مسیرهای `/api/*` را ارائه می‌کند:

```text
مرورگر / نصب PWA / Android / iOS
             |
             v
 دامنهٔ اختصاصی روی Worker عملیاتی
             |
             +---- رابط React/Vite و مسیرهای /app/*
             |
             +---- API احراز هویت‌شده /api/*
                              |
                              v
                       PostgreSQL / Neon
```

مزیت اصلی این مدل این است که مرورگر برای ورود و درخواست‌های API از یک origin استفاده می‌کند؛ در نتیجه به فهرست CORS مجزا برای فرانت‌اند نیاز نیست. حساب‌ها، جلسات، نقش‌ها و داده‌ها در سرور می‌مانند و افزودن سایت یا اپ جدید، دیتابیس جداگانه‌ای ایجاد نمی‌کند.

برای اتصال hostname سفارشی به Worker، دامنه باید از مسیر موردپشتیبانی Cloudflare برای آن hostname قابل‌مدیریت باشد. اگر DNS یا هاست فعلی «راز صحرا» خارج از Cloudflare باقی بماند و امکان اتصال Worker به دامنه فراهم نباشد، مسیر جایگزین بخش بعد است.

## مسیر جایگزین: فرانت‌اند روی هاست، API روی hostname جدا

در این حالت می‌توان فایل‌های build وب را روی هاست استاتیک قرار داد و API را روی زیردامنه‌ای مانند `api.<دامنه-راز-صحرا>` نگه داشت. برای این کار باید **هر دو** تنظیم زیر با hostname واقعی انجام شوند:

1. هنگام build وب، مقدار `VITE_API_BASE_URL` برابر origin کامل HTTPS مربوط به API باشد؛ مثلاً `https://api.<دامنه-راز-صحرا>`. مقدار را پس از build نمی‌توان با تغییر HTML به‌طور امن و قابل‌اتکا عوض کرد.
2. در تنظیم Worker، origin دقیق فرانت‌اند به `ALLOWED_ORIGINS` اضافه و Worker دوباره منتشر شود. در غیر این صورت درخواست‌های cross-origin دارای credential توسط مرورگر پذیرفته نمی‌شوند.

این دو زیردامنه باید از نظر سیاست cookie، TLS و CORS آزموده شوند. فایل‌های `.env` واقعی، `DATABASE_URL` و توکن‌های انتشار نباید در خروجی وب یا مخزن قرار گیرند.

## آماده‌سازی نصب روی موبایل

مدار دارای manifest و service worker است و کد مشترک Capacitor برای Android/iOS را نگه می‌دارد. برای نصب وب روی صفحهٔ اصلی:

- اپ باید از HTTPS و hostname نهایی باز شود؛ manifest، scope، آیکن‌ها و start URL باید از همان origin قابل‌دسترسی باشند.
- کاربر از گزینهٔ نصب مرورگر یا «افزودن به صفحهٔ اصلی» استفاده می‌کند؛ نمایش prompt خودکار در همهٔ مرورگرها قابل‌تضمین نیست.
- service worker فقط پوسته و assetهای مجاز را cache می‌کند؛ پاسخ‌های API محرمانه نباید cache عمومی شوند.
- پس از تغییر نسخه، آزمون باید هم در پنجرهٔ تازه و هم با service worker از قبل نصب‌شده اجرا شود.
- بسته‌های Capacitor باید با API عملیاتی ساخته شوند، نه Worker دموی عمومی. اسکریپت `scripts/build-mobile.mjs` پیش‌فرض عملیاتی را از `https://medar-ops.dengxiao445.workers.dev` می‌گیرد و با `MEDAR_OPS_API_BASE_URL` قابل تنظیم است. برای build دامنهٔ جدید، origin صحیح را در محیط build بدهید.

## ساخت واقعی حساب و ورود

ثبت‌نام عمومی و کد دعوت خاموش است؛ مدل درست این است که مالک/مدیر از بخش «دسترسی کاربران» حساب تأمین‌کننده، راننده یا کارشناس بسازد. API باید در یک عملیات دیتابیسی، هویت با نام‌کاربری استانداردشده، hash گذرواژه، پروفایل اولیه، عضویت فعال در شرکت و رویداد audit را ثبت کند. سپس همان نام‌کاربری و گذرواژه باید در مسیر واقعی ورود معتبر باشند.

آزمون ظاهر فرم یا پاسخ mock مرورگر، اثبات ساخت حساب در دیتابیس نیست. پیش از پایلوت باید SQL واقعی ایجاد حساب روی PostgreSQL سازگار تست شود و با نشست مالک واقعی یک حساب آزمایشی کنترل‌شده ساخته، ورود آن بررسی و سپس از دیتابیس آزمایشی حذف شود. حساب آزمایشی را در پایگاه دادهٔ تجاری اصلی نسازید. آزمون‌های CI این مخزن داده‌های fixture را در تراکنش rollback می‌کنند؛ این معادل آزمون ورود با حساب واقعی مالک در production نیست.

## انتقال دیتابیس و فایل‌ها

دیتابیس فعلی PostgreSQL است و migrationها در `worker/migrations/` شماره‌گذاری شده‌اند. انتقال به هاست صرفاً با کپی ZIP یا عوض‌کردن یک URL انجام نمی‌شود.

- مقصد باید PostgreSQL سازگار باشد و migrationهای موردنیاز را به ترتیب نسخه اجرا کند؛ از MySQL/MariaDB بدون بازطراحی SQL، انواع داده، توابع و تراکنش‌ها استفاده نکنید.
- پیش از انتقال، backup قابل‌بازیابی تهیه کنید؛ روی دیتابیس تولیدی `--clean` یا migration مخرب اجرا نکنید.
- پس از restore، تعداد رکوردهای جدول‌های هویت، عضویت‌ها و داده‌های عملیاتی، کلیدهای خارجی، فایل‌های خصوصی و رویدادهای audit را با مبدأ تطبیق دهید.
- driver فعلی Worker از `@neondatabase/serverless` استفاده می‌کند. فایل dump برای PostgreSQL قابل‌انتقال است، اما اگر مقصد از endpoint سازگار با Neon پشتیبانی نکند، لایهٔ اتصال دیتابیس باید به driver مناسب runtime مقصد تغییر و جداگانه تست شود؛ تغییر `DATABASE_URL` به‌تنهایی تضمین‌کنندهٔ سازگاری نیست.
- اگر فایل‌های خصوصی روی سرویس جداگانه نگهداری شده‌اند، metadata دیتابیس به‌تنهایی محتوای blobها را منتقل نمی‌کند. منبع فایل، مقصد، checksum، مجوزهای دسترسی و لینک‌های رکورد باید جداگانه تطبیق داده شوند.

## بارگذاری، staging و معیار پذیرش

استقرار تجاری باید ابتدا روی staging مستقل انجام شود. پیش از تغییر DNS:

1. اجرای typecheck، lint، تست واحد، migrationهای کامل روی PostgreSQL تمیز و تست SQL ساخت حساب.
2. آزمون Chromium در عرض‌های دسکتاپ، تبلت و موبایل؛ اندازه‌گیری واقعی فاصله و ارتفاع کارت‌های منو، نه فقط بررسی مقدار CSS `gap`.
3. آزمون ایجاد حساب از UI تا API، ثبت عضویت، ورود با همان رمز، تکمیل پروفایل، خروج، غیرفعال‌کردن حساب و ردشدن کاربر بدون دسترسی.
4. آزمون‌های مثبت و منفی جداسازی شرکت‌ها و نقش‌ها؛ تأمین‌کننده نباید دادهٔ شرکت دیگر و راننده نباید محمولهٔ تخصیص‌نیافته را بخواند.
5. آزمون جریان‌های واقعی ظرفیت، وظیفه، تحویل، مدرک و تسویه روی داده‌های آزمایشی با مسیر بازگشت.
6. اجرای بار همزمان روی staging و اندازه‌گیری latency، خطا، نرخ موفقیت، pool/اتصالات دیتابیس و محدودکنندهٔ ورود.

«۱۰۰ کاربر» فقط زمانی آزمون بار واقعی محسوب می‌شود که درخواست‌های همزمان به یک سرویس staging و دیتابیس وصل شوند. ساخت ۱۰۰۰ نام کاربری یا ۱۰۰ نقش در unit test صرفاً شبیه‌سازی داده است و نباید جای آزمون بار یا اثبات احراز هویت زنده را بگیرد.

## متغیرهای محیطی

| متغیر | محل | کاربرد |
|---|---|---|
| `DATABASE_URL` | فقط secret سمت Worker/API | اتصال PostgreSQL |
| `ALLOWED_ORIGINS` | تنظیم Worker | فهرست originهای دقیق مجاز وقتی وب و API دو origin هستند |
| `VITE_API_BASE_URL` | زمان build وب/موبایل | origin API عمومی؛ هیچ secretی در آن قرار نمی‌گیرد |
| `MEDAR_OPS_API_BASE_URL` | محیط build Capacitor | origin API عملیاتی نسخهٔ native |
| `VITE_ENABLE_AUTH_UI` | زمان build | فعال‌سازی UI ورود عملیاتی |

## وضعیت

- [x] migrationهای PostgreSQL نسخه‌بندی شده‌اند.
- [ ] دامنهٔ واقعی «راز صحرا» و DNS/هاست آن به این نسخه متصل شده است.
- [ ] نسخهٔ PWA پس از استقرار روی hostname نهایی در دستگاه‌های واقعی نصب/به‌روزرسانی آزمایش شده است.
- [ ] انتقال دیتابیس و فایل‌های واقعی به هاست مقصد اجرا و تطبیق داده شده است.
- [ ] ورود و گردش‌کارها با حساب‌های واقعی staging و آزمون بار همزمان اندازه‌گیری شده‌اند.

کادرهای تکمیل‌نشده عمداً به‌عنوان انجام‌شده گزارش نشده‌اند؛ برای انجامشان دسترسی به DNS/هاست و محیط staging لازم است.


## خروجی عملیاتی برای هاست اشتراکی و مهاجرت PostgreSQL

برای تولید خروجی وبِ دارای ورود واقعی، از **نسخهٔ build عملیاتی** استفاده کن، نه build:pages؛ آن خروجی برای دموی ایستا است.

Linux/macOS:

    MEDAR_WEB_API_BASE_URL="https://medar-ops.dengxiao445.workers.dev" npm run build:hosted-web

PowerShell:

    $env:MEDAR_WEB_API_BASE_URL = "https://medar-ops.dengxiao445.workers.dev"
    npm run build:hosted-web

این فرمان مبدأ API را اعتبارسنجی می‌کند، UI ورود خصوصی را فعال می‌کند، اتصال به API دموی عمومی را رد می‌کند و خروجی dist/ را برای میزبانی ریشه‌ای بررسی می‌کند. سپس **محتویات** dist/ را در document root زیردامنهٔ اپ بارگذاری کن؛ خود پوشهٔ dist را به‌عنوان زیرپوشهٔ اضافی کپی نکن. فایل .htaccess همراه خروجی، مسیرهای داخلی مانند /app/home را به SPA هدایت می‌کند و فایل‌های واقعی را مستقیم سرو می‌کند. این روش فقط زمانی مناسب است که Apache و mod_rewrite فعال باشند؛ برای Nginx باید معادل fallback در پیکربندی وب‌سرور تعریف شود.

اگر فرانت‌اند و API دو مبدأ متفاوت دارند، متغیر GitHub Actions به نام MEDAR_ALLOWED_ORIGINS باید مبدأ HTTPS دقیق فرانت‌اند را دربر بگیرد و Worker بعد از آن دوباره منتشر شود. فایل dist/medar-deployment.json فقط نسخهٔ عمومی build و origin API را نشان می‌دهد؛ رمز دیتابیس، توکن Cloudflare یا گذرواژهٔ کاربران نباید در آن قرار گیرد.

### ابزارهای انتقال دیتابیس

در این مخزن سه ابزار محافظه‌کارانه اضافه شده‌اند:

    # 1) بکاپ custom-format از PostgreSQL مبدأ
    SOURCE_DATABASE_URL="$SOURCE_DATABASE_URL" bash scripts/export-postgres.sh backups/medar

    # 2) بازیابی فقط به دیتابیس خالی و جداگانه
    TARGET_DATABASE_URL="$TARGET_DATABASE_URL" bash scripts/restore-postgres.sh backups/medar/medar-postgres-YYYYMMDDTHHMMSSZ-123.dump

    # 3) مقایسهٔ تعداد رکوردهای کلیدی پیش از cutover
    SOURCE_DATABASE_URL="$SOURCE_DATABASE_URL" TARGET_DATABASE_URL="$TARGET_DATABASE_URL" bash scripts/compare-postgres-databases.sh

فرمان نمونه فقط قالب دستور را نشان می‌دهد؛ مسیر dump واقعی را از خروجی مرحلهٔ اول بردار. بکاپ شامل داده‌های حساس است و باید در فضای خصوصی با مجوز محدود نگه‌داری شود. اسکریپت restore در دیتابیس مقصد شیءهای موجود را پاک نمی‌کند؛ اگر مقصد خالی نباشد، عمداً متوقف می‌شود. شمار رکوردها فقط کنترل اولیه است، نه اثبات برابری کامل. پیش از تغییر ترافیک، کلیدهای خارجی، migration ledger، فایل‌های ذخیره‌شده، نشست‌ها و جریان‌های نقش‌محور نیز باید بررسی شوند.

**نکتهٔ معماری:** خروجی وب، بک‌اند و دیتابیس سه چیز جدا هستند. آپلود dist/ به هاست اشتراکی، به‌تنهایی API را به PHP/MySQL تبدیل نمی‌کند. API فعلی روی Cloudflare Workers و PostgreSQL/Neon ساخته شده است. اگر مقصد نهایی PostgreSQL دیگری است که با درایور فعلی سازگار نیست، ابتدا آداپتور/درایور اتصال و تراکنش‌ها باید روی staging پورت و تست شود؛ روی دیتابیس تولیدی driver را با تعویض URL آزمایش نکن.
