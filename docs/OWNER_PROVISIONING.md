# مدار — ساخت حساب اعضا و دسترسی اولیه

## مدل دسترسی در نسخهٔ عملیاتی

مدار در محیط عملیاتی یک سامانهٔ خصوصی است. ثبت‌نام عمومی در `POST /api/auth/signup` با HTTP 403 و ثبت‌نام با کد دعوت در `POST /api/auth/signup-with-invite` با HTTP 410 رد می‌شود. بنابراین راهنمای قدیمی ثبت‌نام عمومی و پیوستن با کد دعوت، روش جاری استفاده از مدار نیست.

حساب همکاران از پنل «دسترسی کاربران» توسط مالک یا مدیر مجاز همان مجموعه ساخته می‌شود. API دوباره نقش و عضویت سمت سرور را بررسی می‌کند؛ مخفی بودن دکمه یا نقش نمایش‌داده‌شده در مرورگر به‌تنهایی مجوز محسوب نمی‌شود.

- **مالک `owner`:** می‌تواند مدیر `admin`، کارشناس `staff`، تأمین‌کننده `supplier` و راننده `driver` ایجاد کند.
- **مدیر `admin`:** می‌تواند کارشناس، تأمین‌کننده و راننده ایجاد کند؛ اجازهٔ ساخت مدیر جدید را ندارد.
- **کارشناس، تأمین‌کننده و راننده:** اجازهٔ ساخت حساب یا تغییر نقش خود را ندارند.
- نقش `customer` دیگر نقش قابل ساخت در نسخهٔ عملیاتی نیست و مسیرهای سفارش‌گیری مشتری فعال نیستند. رکوردهای قدیمی مشتری برای حفظ داده و سازگاری نگه داشته می‌شوند؛ حذف نشده‌اند.

## ساخت حساب در پنل

1. با حساب مالک یا مدیر مجاز وارد شو و از «دسترسی کاربران» گزینهٔ «ساخت حساب جدید» را انتخاب کن.
2. نام کاربری یکتا با ۳ تا ۳۲ نویسه وارد کن. حروف، عدد، نقطه، خط تیره و زیرخط مجازند؛ نام کاربری نباید با نقطه، خط تیره یا زیرخط آغاز یا پایان یابد. مدار مقدار را عادی‌سازی می‌کند؛ برای جلوگیری از اشتباه، از نام کاربری نهایی نمایش‌داده‌شده استفاده کن.
3. رمز اولیه‌ای یکتا با ۱۲ تا ۱۲۸ نویسه انتخاب کن. آن را از طریق پیام‌رسان عمومی، گروه یا ticket ارسال نکن.
4. نقش درست را انتخاب کن. برای تأمین‌کننده، می‌توان پروندهٔ موجود همان مجموعه را متصل کرد؛ اگر پرونده‌ای انتخاب نشود، Worker پروندهٔ تأمین اولیه ایجاد می‌کند.
5. پس از پاسخ موفق سرور، مدار وجود عضویت و نقش صحیح را کنترل می‌کند. اطلاعات ورود فقط بعد از تأیید پاسخ نمایش داده می‌شود. اگر پیام خطا ظاهر شد، ساخت حساب را موفق فرض نکن و قبل از تلاش مجدد فهرست را تازه‌سازی کن.
6. رمز را فقط از مسیر امن به صاحب حساب تحویل بده. رمز موقت را در تاریخچه، اسکرین‌شات یا کانال عمومی نگه ندار.

حساب باید هویت، پروفایل، عضویت و رویداد ممیزی لازم را به‌صورت سازگار ایجاد کند. اگر ساخت کامل نشد، پیام خطای Worker را بررسی کن، اما secret، رمز، cookie و رشتهٔ اتصال دیتابیس را در log یا گفتگو قرار نده.

## اولین ورود و تکمیل پروفایل

کاربر با **نام کاربری و رمز عبور** وارد می‌شود؛ شماره تلفن برای تکمیل پروفایل پس از ورود جمع‌آوری می‌شود، نه به‌عنوان شناسهٔ ورود.

- همهٔ کاربران باید نام، نام خانوادگی و شماره تلفن را تکمیل کنند.
- تأمین‌کننده علاوه بر آن باید استان، شهر و نشانی محل فعالیت را وارد کند تا پروندهٔ کاری او قابل پیگیری باشد.
- راننده و تأمین‌کننده فقط رکوردهایی را می‌بینند که در عضویت و دامنهٔ مجاز همان مجموعه به آن‌ها مرتبط شده‌اند.
- کاربر نمی‌تواند از فرم تکمیل پروفایل نقش خود را عوض کند.

## بازنشانی رمز و بستن دسترسی

مالک یا مدیر مجاز می‌تواند از فهرست اعضا رمز را بازنشانی کند یا عضویت را غیرفعال کند. بازنشانی رمز نشست‌های قبلی کاربر را باطل می‌کند. رمز تازه را فقط به صاحب حساب تحویل بده. پس از خروج عضو از مجموعه، دسترسی او را غیرفعال کن و حذف رکوردهای تاریخی را جایگزین این کار نکن.

## راه‌اندازی اولین مالک

هیچ حساب پیش‌فرض یا رمز پیش‌فرضی در انتشار ساخته نمی‌شود و مسیر ثبت‌نام عمومی هم عمداً بسته است. بنابراین برای یک استقرار کاملاً تازه، پیش از ساخت اعضا باید دست‌کم یک حساب مالک به‌وسیلهٔ اپراتور مجاز، از روش provisioning مورد تأیید محیط مقصد ایجاد شده باشد.

اگر هنوز مالک فعالی وجود ندارد، از SQL دست‌ساز روی دیتابیس تولیدی یا از بازکردن ثبت‌نام عمومی به‌عنوان راه‌حل موقت استفاده نکن. راه‌اندازی اولین مالک باید با یک فرایند اپراتوری مستند، احرازشده، قابل ممیزی و آزمایش‌شده انجام شود. تا زمانی که این روش برای محیط موردنظر تأیید نشده، ایجاد workspace جدید از مسیر self-service پشتیبانی‌شده محسوب نمی‌شود.

## صحت‌سنجی و مرز ادعاها

CI فعلی زنجیرهٔ migration، SQL ساخت عضو، نام کاربری عادی‌شده، نقش‌ها، عضویت‌های محدود به مجموعه، profile و audit event را روی PostgreSQL موقت می‌آزماید. آزمون‌های مرورگر تعامل UI را با API ایزوله بررسی می‌کنند؛ این آزمون‌ها به‌تنهایی موفقیت حساب واقعی را در دیتابیس تولیدی اثبات نمی‌کنند.

برای پذیرش واقعی باید مالک مجاز از پنل زنده یک حساب کاری مورد تأیید کسب‌وکار بسازد، کاربر با آن وارد شود، پروفایل را تکمیل کند، مجوزهای مورد انتظار را بررسی کند و خروج/ابطال نشست را آزمایش کند. رمز یا cookie را با تیم توسعه در گفتگو به اشتراک نگذار.

## اسرار و داده‌ها

- رمز عبور، session cookie، کد خصوصی و secret محیط را در گفتگو، issue، log یا مخزن قرار نده.
- `DATABASE_URL` و Cloudflare token فقط در secret store سمت سرور و CI قرار می‌گیرند، نه در `VITE_*` یا bundle مرورگر.
- پیش از هر migration، پروژه و branch واقعی Neon را بررسی کن؛ فایل‌های تاریخی `supabase/migrations/` را یک‌جا روی Neon اجرا نکن.
- دادهٔ تجاری قدیمی به‌صورت خودکار به Neon منتقل نشده است. مهاجرت داده باید با backup قابل بازیابی، تطبیق schema، مقایسهٔ شمارش و روابط، dry-run و تأیید مالک داده جداگانه انجام شود.
