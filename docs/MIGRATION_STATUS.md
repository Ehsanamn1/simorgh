## معماری و مرز محیط‌ها

`React/Vite SPA → Cloudflare Worker → Neon PostgreSQL`

- `medar-ops` محیط عملیاتی است؛ برای دسترسی به داده‌ها، نشست نام‌کاربری/رمز عبور و عضویت تأییدشدهٔ سمت سرور لازم است.
- `medar-api` و Pages دمو هستند؛ API دمو فقط‌خواندنی است و ورودی عمومی به محیط عملیاتی هدایت می‌شود.
- نقش runtime برای Worker عملیاتی با `MEDAR_DEPLOYMENT_MODE=operational` به‌صورت صریح تنظیم می‌شود. `MEDAR_DEPLOYMENT_MODE` بر متغیر سازگاری قدیمی `MEDAR_MODE` اولویت دارد تا mode دمو به‌اشتباه عملیاتی را override نکند. bootstrap و Worker نمایشی پیکربندی جدا دارند.
- نشست‌های عملیاتی با کوکی `HttpOnly` و توکن نشست هش‌شده مدیریت می‌شوند. نقش و محدودهٔ شرکت از عضویت سمت سرور تعیین می‌شود؛ مقدار `company_id` یا `role` ارسالی مرورگر برای اعطای دسترسی کافی نیست.

## احراز هویت و مجوزها — وضعیت آزمون‌شده

انتشار [run 39653283449](https://github.com/Ehsanamn1/simorgh/actions/runs/39653283449) تأیید کرد:

- Health محیط عملیاتی `ok: true`، `service: "medar-ops"`، `database: true` و احراز هویت username/password را برمی‌گرداند.
- ثبت‌نام عمومی و ثبت‌نام با کد دعوت غیرفعال‌اند؛ تکمیل پروفایل و دسترسی workspace بدون نشست رد می‌شوند.
- UI ورود در مرورگر Chromium روی دسکتاپ و موبایل render می‌شود؛ مسیرهای مستقیم عملیاتی به صفحهٔ ورود محافظت‌شده می‌رسند.
- درخواست تغییردهنده از origin ناشناس با 403 رد می‌شود؛ preflightهای credentialed مربوط به `capacitor://localhost` و `https://localhost` آزموده شده‌اند.
- ورودی عمومی همچنان دمو باقی می‌ماند و به محیط عملیاتی هدایت می‌شود؛ API دمو ثبت‌نام/ورود و دسترسی workspace را رد می‌کند.

قابلیت ایجاد عضو جدید از پنل مجاز مالک/مدیر محدود به نقش‌های عملیاتی `admin`, `staff`, `supplier`, `driver` است. ساخت حساب جدید مشتری و UI سفارش‌گیری/کاتالوگ مشتری در محیط عملیاتی غیرفعال شده‌اند. API علاوه بر پنهان‌کردن لینک‌ها، ایجاد `orders` و `order_items` از نقش مشتری را نیز رد می‌کند و ارسال/لغو سفارش مشتری مجاز نیست. عضویت‌ها و داده‌های قدیمی مشتری حذف نشده‌اند و فقط برای سازگاری با خواندن محدودِ مجاز حفظ می‌شوند؛ سفارش‌های داخلی را کاربران داخلی مجاز مدیریت می‌کنند. CI و Playwright این مرز و دسترسی routeهای کیفیت/مالی شریک/تسویه را بررسی می‌کنند.

**هنوز نیازمند پذیرش انسانی:** آزمون کامل توسط مالک مجاز که از پنل حساب واقعی کارمند/تأمین‌کننده/راننده ایجاد شود، همان حساب وارد شود و مجوزهای مجاز/غیرمجاز همان نقش از رابط کاربری واقعی بررسی شود. این تست با یک حساب ساختگی در دیتابیس تولید انجام نشده و رمز عبور نباید در گفتگو ثبت شود.

## دیتابیس و migration

- CI اصلی، زنجیرهٔ کامل migrationها را روی PostgreSQL 16 تمیز، typecheck، lint، unit tests، تست‌های SQL، تست‌های مرورگر desktop/mobile/auth/operations، buildهای PWA و Worker اجرا می‌کند.
- انتشار روی Worker عملیاتی ابتدا وجود schema مستقر و جدول‌های پایه را بررسی می‌کند؛ سپس migrationهای سازگاری نسخه‌دار و checksumدار `0007–0031` را اعمال/تأیید می‌کند و وجود RPCها، ledger migration و ساختار لازم حساب اعضا را بررسی می‌کند. این مسیر عمداً schema اولیه را روی دیتابیس خالی یا نامرتبط replay نمی‌کند.
- CI، SQL واقعی ایجاد حساب عضو و restore آزمایشی `pg_dump`/`pg_restore` را روی دیتابیس موقت بررسی می‌کند. این شواهد اثبات می‌کنند مسیر فنی migration/backup در محیط آزمون کار می‌کند؛ جایگزین بازیابی یک backup واقعی Production نیستند.
- **مهاجرت داده از Supabase قدیمی تأیید نشده است.** هیچ تطبیق ردیف‌به‌ردیف، dry run انتقال یا rollback end-to-end در این انتشار ادعا نمی‌شود. پیش از انتقال، باید منبع صحیح و دسترسی آن مشخص شود، backup قابل‌بازیابی گرفته شود، شمار رکوردها/روابط مقایسه شود و rollback مستند و تأیید شود. در همین PRها دادهٔ تجاری قدیمی حذف یا بازنویسی نشده است.
- شناسهٔ دیتابیس و تعداد رکوردی که در بازبینی قبلی گزارش شده بود، snapshot تاریخی همان بازبینی است و نباید به‌عنوان شمارش زندهٔ امروز استفاده شود؛ پیش از تصمیم انتقال داده، query خواندنی جدید لازم است.

## فایل خصوصی و ذخیره‌سازی

R2 در این حساب همچنان تضمین‌شده/فعال فرض نمی‌شود. کد و schema فعلی fallback خصوصی دیتابیس برای فایل‌ها را دارد و سقف هر فایل در fallback برابر ۱۰ مگابایت است؛ workflow انتشار وجود ستون `medar_files.content_base64` را بررسی می‌کند. بنابراین نبود binding R2 به‌تنهایی به این معنی نیست که تمام routeهای فایل HTTP 503 می‌دهند.

بااین‌حال، انتشار فعلی **پذیرش زندهٔ کامل فایل را اثبات نکرده است**. قبل از استفادهٔ تجاری باید فایل کوچک آزمایشی از طریق مسیر مجاز بارگذاری شود، بازیابی مجاز و غیرمجاز بررسی شود، حذف فایل و رفتار backup/recovery آزموده شود، و سقف اندازه/حجم عملیاتی مستند شود. اگر بار عملیاتی یا فایل بزرگ‌تر لازم است، R2 را فعال کنید و مسیر خصوصی را با همان تست‌ها smoke-test کنید. تا انجام آن، ذخیره‌سازی فایل را قابلیت تجاریِ پذیرفته‌شده معرفی نکنید.

## مالی، عملیات و AI — سطح ادعا

- **عملیات/انبار/وظایف/کیفیت/تسویه شریک:** CI و تست‌های دیتابیس/مرورگر گردش‌های منتخب مانند مجوزهای نقش، هم‌زمانی موجودی، lifecycle سفارش خرید، کنترل انتقال وضعیت و تسویه را آزموده‌اند. این به‌تنهایی اثبات اجرای end-to-end با رکورد تجاری و کاربران واقعی نیست.
- **پرداخت بانکی بیرونی:** اتصال یا اجرای پرداخت بانکی بیرونی در این وضعیت ادعا نمی‌شود.
- **AI:** پشتیبانی تنظیمات ارائه‌دهنده و رمزنگاری کلیدها در کد وجود دارد، اما وجود پیکربندی فعال ارائه‌دهنده و اجرای درخواست واقعی باید جداگانه تأیید شود. کلیدهای API فقط در سمت سرور نگه‌داری شوند.
- **Web Push:** workflow مجموعهٔ کلیدهای VAPID را حفظ می‌کند یا در نبودشان کلید پایدار تولید/ثبت می‌کند، اما پاسخ زندهٔ `/api/push/config` با نشست معتبر مالک هنوز در این release از طریق حساب واقعی تأیید نشده است؛ تا آن زمان push را از نظر end-to-end پذیرفته‌شده معرفی نکنید.
- **Offline writes:** صف نوشتن آفلاین، retry/idempotency، حل تعارض و بازیابی کامل پیاده/تأیید نشده‌اند؛ وعدهٔ همگام‌سازی آفلاین کامل ندهید.

## تصمیم آمادگی تجاری

**NO-GO برای عرضهٔ تجاری گسترده در این مرحله.** زیرساخت و release، health/runtime mode، امنیت routeهای بی‌نشست، CI، buildهای Android/iOS و اتصال از مسیر Raz Sahra تأیید شده‌اند؛ ولی پذیرش مالک با نقش‌های واقعی، تست زندهٔ فایل، آزمون authenticated Web Push config و تصمیم رسمی دربارهٔ انتقال دادهٔ قدیمی هنوز گیت‌های باز هستند.

تکمیل گیت‌های تجاری و go/no-go با checklist مستقل [docs/COMMERCIAL_PILOT_READINESS.md](./COMMERCIAL_PILOT_READINESS.md) پیگیری می‌شود.

## قواعد ادامه

- migration اعمال‌شده را درجا ویرایش نکنید؛ schema change فقط افزایشی، تکرارپذیر و checksumدار باشد.
- هیچ credential یا کلید API در سورس یا `VITE_*` قرار ندهید و رمز عبور را در issue/comment/chat ننویسید.
- قبل از هر پاک‌سازی/انتقال، منبع، backup قابل‌بازیابی و rollback را تأیید کنید.
- دمو را سند وجود دادهٔ عملیاتی واقعی فرض نکنید.
- حالت Worker عملیاتی و حالت demo را از هم جدا نگه دارید؛ آزمون سلامت باید `service: "medar-ops"` و اتصال دیتابیس را تأیید کند.
