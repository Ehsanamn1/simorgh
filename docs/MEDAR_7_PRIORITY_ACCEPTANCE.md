# مدار — اجرای هفت اولویت محصول

تاریخ بازبینی: ۱۷ اکتبر ۲۰۲۶  
شاخه پیاده‌سازی: `feature/medar-full-product-hardening`

این سند تفکیک می‌کند چه چیزی در سورس موجود است، چه چیزی با تست پوشش دارد و چه چیزی هنوز برای استفاده واقعی اثبات نشده است. وجود صفحه یا endpoint به‌تنهایی به معنی تکمیل قابلیت نیست.

## تصمیم‌های ثابت معماری

- احراز هویت با **نام کاربری + رمز عبور**؛ شماره موبایل ایران برای ثبت‌نام و ارتباط عملیاتی لازم است.
- بدون ایمیل اجباری، لینک بازیابی ایمیل یا SMS OTP.
- نشست در کوکی HttpOnly و توکن نشست هش‌شده در پایگاه داده؛ رمز با PBKDF2-SHA-256 هش می‌شود.
- Cloudflare Worker + Neon به‌عنوان معماری مقصد؛ GitHub Actions برای تست و انتشار.
- هیچ R2 جدیدی ساخته نمی‌شود. بارگذاری فایل‌هایی که هنوز به R2 وابسته‌اند تا انتخاب و پیاده‌سازی ذخیره‌ساز جایگزین، قابلیت آماده برای عملیات محسوب نمی‌شود.
- داده‌های Supabase تا تهیه پشتیبان، تطبیق طرح و مهاجرت قابل بازگشت نباید حذف شوند.

## محدودیت‌های شناخته‌شده

- بازیابی خودکار رمز بدون ایمیل/SMS در این نسخه ارائه نمی‌شود. مالک/مدیر می‌تواند از مسیر مجاز، اطلاعات ورود عضو را بازنشانی کند.
- مسیرهای فایل و مدرک که به binding ذخیره‌سازی R2 وابسته‌اند، تا زمان ساخت آداپتور ذخیره‌ساز جایگزین فعال محسوب نمی‌شوند. این تصمیم عمدی است و نباید با اتصال خودکار R2 دور زده شود.
- مهاجرت داده‌های عملیاتی قدیمی Supabase هنوز اثبات نشده است. وجود دو سیستم به معنی همگام‌سازی داده نیست.
- ساخت موفق CI، جایگزین تست واقعی نقش‌ها، صحت مالی، پشتیبان‌گیری و بازیابی نیست.

## ترتیب اجرا

1. سبزکردن typecheck/lint/unit/E2E روی همین تغییرات.
2. انتشار آزمایشی Worker و تست تغییر رمز و مسیرهای احراز هویت.
3. تست tenant isolation و نقش‌ها با حساب‌های واقعی آزمایشی.
4. تکمیل و اثبات جریان‌های سفارش/انبار/تولید/ارسال/مالی.
5. انتخاب ذخیره‌ساز جایگزین R2 و اجرای تست دسترسی فایل.
6. مهاجرت کنترل‌شده Supabase با پشتیبان و reconciliation؛ فقط بعد از پذیرش، حذف وابستگی قدیمی.
7. پیاده‌سازی آفلاین/هوش عملیاتی پس از قابل اتکا شدن داده‌ها.

تا زمانی که هر معیار پذیرش تست و مدرک اجرا نداشته باشد، آن مورد «در حال تکمیل» است و نباید به‌عنوان قابلیت تولیدی تبلیغ شود.
