# مدار — اپلیکیشن موبایل

سایت مدار و اپلیکیشن‌های Android/iOS از یک برنامه‌ی React/TypeScript مشترک استفاده می‌کنند؛ Capacitor همان رابط، منوها، فرم‌ها، نقش‌ها و گردش‌کارها را در پوسته‌ی موبایل اجرا می‌کند. دیتابیس و API در سمت سرور هستند و نباید برای نسخه‌ی موبایل، منطق دسترسی یا داده‌های عملیاتی جداگانه و ضعیف‌تری ساخته شود.

## معماری اجرایی

`React/Vite → Capacitor WebView → Cloudflare Worker API → Neon PostgreSQL`

- فضای نمایشی عمومی `medar-api` فقط‌خواندنی است و داده‌های نمونه را با برچسب نمایش می‌دهد.
- فضای عملیاتی احراز هویت‌شده در `medar-ops` قرار دارد؛ اپ عملیاتی موبایل باید به همین API وصل باشد، نه اینکه از دموی عمومی به‌عنوان فضای کاری واقعی استفاده کند.
- نشست و مجوزها باید سمت Worker تأیید شوند. شناسه‌ی شرکت یا نقش دریافتی از رابط کاربری به‌تنهایی مجوز محسوب نمی‌شود.
- همه‌ی کلاینت‌ها از قرارداد مشترک `src/lib/runtimeConfig.ts` و مقصد `VITE_API_BASE_URL` استفاده می‌کنند. بسته‌ی موبایل باید مقصد احرازشده‌ی `medar-ops` را در build دریافت کند؛ از `medar-api` که دمو عمومی است استفاده نکن.
- پس از ورود، وب و اپ موبایل هر ۶۰ ثانیه یک heartbeat کم‌حساسیت به API مرکزی می‌فرستند. مدیر/مالک وضعیت API، دیتابیس و آخرین فعالیت وب/Android/iOS را در «مرکز اتصال مدار» می‌بیند. آنلاین بودن یعنی heartbeat در سه دقیقه‌ی اخیر؛ این فقط نشانگر آخرین فعالیت است و دسترسی ایجاد نمی‌کند.
- ورود عملیاتی وب و موبایل فقط با نام کاربری و رمز عبور انجام می‌شود؛ شماره موبایل، ایمیل و OTP پیامکی لازم نیستند.
- روی موبایل، انتخاب حالت روشن/تاریک در تنظیم مشترک `simorgh-theme` ذخیره می‌شود. ظاهر، رنگ نوار وضعیت و خوانایی پوسته باید هماهنگ بمانند؛ انتخاب تم هیچ‌گونه دسترسی عملیاتی ایجاد نمی‌کند.
- رابط اصلی فارسی و راست‌چین با فونت Vazirmatn است و باید در عرض‌های کم، با ناحیه‌های امن دستگاه، صفحه‌کلید، چرخش صفحه و تنظیم کاهش حرکت سیستم سازگار باشد.

## ساخت Android برای آزمون داخلی

Workflow با نام `Simorgh Android App` در GitHub Actions یک APK آزمایشی debug می‌سازد. این فایل برای نصب داخلی است، امضای انتشار فروشگاهی محسوب نمی‌شود. از خروجی workflow موفق، artifact با نام `simorgh-android-debug-apk` را دریافت و روی دستگاه آزمایشی نصب کن.

محیط محلی به Node.js 22+، Android Studio و Android SDK نیاز دارد:

```sh
npm install
npm run mobile:android:prepare
npx cap open android
```

## ساخت iOS

ساخت و اجرای اپ iOS به macOS و Xcode نیاز دارد. Workflow شبیه‌ساز، خروجی مناسب آزمون در شبیه‌ساز تولید می‌کند، نه اپ امضاشده برای دستگاه واقعی:

```sh
npm install
npm run mobile:ios:prepare
npx cap open ios
```

## محدودیت‌های انتشار

- APK فعلی خروجی debug و بدون امضای انتشار است؛ انتشار در Google Play به keystore محافظت‌شده و مجوزهای فروشگاه نیاز دارد.
- نصب روی iPhone واقعی یا TestFlight به Apple Developer Team، گواهی و provisioning نیاز دارد.
- کلیدها، گذرواژه‌ها، توکن‌های انتشار یا secrets نباید در سورس، bundle فرانت‌اند یا فایل ZIP عمومی قرار گیرند.
- Cloudflare R2 تا فعال‌سازی و آزمون binding و مسیرهای upload/read غیرفعال است؛ endpoint فایل در این وضعیت نباید به‌عنوان قابلیت فعال معرفی شود.
- انتقال داده‌های قدیمی به Neon، راه‌اندازی حساب واقعی مالک و پذیرش end-to-end همه نقش‌ها باید جداگانه اثبات شوند.
- GPS پس‌زمینه، push notification، اسکن بارکد، صف نوشتن آفلاین و حل تعارض هنوز جریان تولیدی کامل و تأییدشده محسوب نمی‌شوند.
- انتشار فروشگاهی فقط پس از آزمون امنیت، جداسازی شرکت‌ها، کنترل نقش‌ها، سناریوهای منفی، گردش‌کار تجاری و signing مجاز است.

## معیار آزمون قبل از انتشار موبایل

1. نصب و بازکردن برنامه در دستگاه یا شبیه‌ساز، شامل لینک مستقیم و refresh داخلی.
2. ورود و خروج واقعی، بازسازی نشست و آزمون خطای رمز عبور؛ پشتیبانی از ارقام فارسی و قالب‌های `09`، `+98` و `0098`.
3. تأیید حالت روشن و تاریک قبل و بعد از restart، همگام‌سازی status bar، کنتراست، فونت و RTL.
4. آزمون ابعاد کوچک، safe areas، صفحه‌کلید، overflow و `prefers-reduced-motion`.
5. آزمون هر نقش با حساب جدا: کاربر یک شرکت نتواند رکوردهای شرکت دیگر یا سفارش/محموله‌ی تخصیص‌نیافته را بخواند یا تغییر دهد.
6. آزمون سرتاسری سفارش، تأیید خرید، رسید جزئی/نهایی، موجودی، تحویل و اسناد مالی روی داده‌های کنترل‌شده.

ساخت موفق APK یا اپ شبیه‌ساز به‌تنهایی به معنی تکمیل یا تأیید این سناریوها نیست.
