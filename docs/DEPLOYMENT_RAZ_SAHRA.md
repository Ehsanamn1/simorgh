# استقرار مدار روی دامنهٔ «راز صحرا» و آماده‌سازی انتقال داده

این راهنما مسیر استقرار را طوری جدا می‌کند که سایت اصلی راز صحرا دست‌نخورده بماند، کاربران از یک آدرس اختصاصی وارد مدار شوند و دیتابیس و فایل‌های برنامه از فرانت‌اند قابل دسترسی مستقیم نباشند.

## معماری فعلی

- **رابط وب/PWA:** React + Vite؛ راست‌چین، قابل نصب از مرورگر و با مسیرهای داخلی `/app/...`.
- **API و احراز هویت:** Cloudflare Worker با نام `medar-ops`. ورود با نام کاربری/رمز عبور انجام می‌شود؛ ثبت‌نام عمومی بسته است.
- **داده‌ها:** PostgreSQL سازگار با Neon، با ۳۱ مهاجرت نسخه‌بندی‌شده در پوشهٔ `worker/migrations`.
- **کلاینت موبایل:** Capacitor برای Android و iOS؛ نسخهٔ موبایل هم باید به همان API عملیاتی متصل شود.
- **اصل امنیتی:** آدرس دیتابیس و رازهای سمت سرور فقط در Worker Secrets هستند؛ هیچ‌کدام نباید داخل `VITE_*` یا فایل‌های استاتیک قرار بگیرند.

تمام عملیات وب از مسیرهای `/api/...` عبور می‌کند؛ مرورگر نباید مستقیماً به PostgreSQL وصل شود.

## گزینهٔ پیشنهادی: یک زیردامنهٔ اپلیکیشن

آدرس پیشنهادی **`app.<دامنه-راز-صحرا>`** است؛ دامنهٔ اصلی سایت بازاریابی/فروش راز صحرا روی میزبان فعلی خودش می‌ماند.

1. اگر DNS دامنه در Cloudflare مدیریت می‌شود، در Cloudflare به **Workers & Pages → medar-ops → Settings → Domains & Routes → Add → Custom Domain** برو و زیردامنهٔ اختصاصی اپ را اضافه کن. Cloudflare برای زیردامنه رکورد DNS و گواهی TLS را تنظیم می‌کند.
2. در GitHub مخزن `Ehsanamn1/simorgh`، بخش **Settings → Secrets and variables → Actions → Variables** متغیر `MEDAR_OPS_API_BASE_URL` را روی مبدأ نهایی اپ بگذار؛ نمونه: `https://app.example.ir`. فقط مبدأ را قرار بده، بدون مسیر یا اسلش انتهایی.
3. اگر فرانت‌اند و API روی همین Worker و همین مبدأ سرو شوند، درخواست‌ها same-origin هستند و برای مسیر معمول وب نیازی به CORS بین‌دامنه‌ای نیست.
4. اجرای workflow انتشار را بررسی کن و سپس این مسیرها را روی زیردامنهٔ جدید تست کن: `/`, `/app/home`, `/api/health`, ورود، خروج و نصب PWA.

**مهم:** نام دامنهٔ واقعی در این مخزن ثبت نشده و این راهنما DNS واقعی را تغییر نمی‌دهد. رکورد دامنهٔ اصلی سایت را حذف یا جایگزین نکن؛ ابتدا زیردامنهٔ اپ را به Worker متصل کن. دامنهٔ سفارشی Worker به یک Cloudflare zone فعال نیاز دارد و نباید از قبل CNAME متعارضی روی همان hostname وجود داشته باشد.

## اگر هاست اشتراکی باید فایل‌های وب را سرو کند

در این حالت Worker همچنان API و دیتابیس را اداره می‌کند؛ هاست اشتراکی فقط خروجی فایل‌های `dist` را میزبانی می‌کند.

1. خروجی عملیاتی را با `VITE_ENABLE_AUTH_UI=true` و `VITE_API_BASE_URL=https://medar-ops.dengxiao445.workers.dev` بساز و **محتویات** پوشهٔ `dist` را روی زیردامنهٔ اپ قرار بده؛ پوشهٔ `dist` را به صورت یک زیرپوشهٔ اضافی منتشر نکن.
2. روی هاست، fallback برنامهٔ تک‌صفحه‌ای را طوری تنظیم کن که مسیرهای مجازی مانند `/app/home` به `index.html` برسند اما فایل‌های موجود JS/CSS/SVG/manifest مستقیماً سرو شوند.
3. در GitHub Actions variable به نام `MEDAR_ALLOWED_ORIGINS`، مبدأ دقیق فرانت‌اند را ثبت کن؛ برای مثال `https://app.example.ir`. چند مبدأ را با کاما جدا کن؛ از مسیر یا اسلش انتهایی استفاده نکن. workflow این مبدأها را با مبدأهای توسعهٔ موجود ترکیب می‌کند و CORS زنده را بررسی می‌کند.
4. مطمئن شو مرورگر به API عملیاتی HTTPS وصل می‌شود؛ آدرس `medar-api` که حالت نمایش عمومی دارد، برای حساب‌های واقعی استفاده نشود.

## نصب روی موبایل

- برای نصب وب‌اپ از مرورگر، صفحه باید روی HTTPS باشد و manifest و service worker با همان مسیر نصب شوند. در Android/Chrome یا Edge دکمهٔ **نصب مدار** در تنظیمات از prompt بومی نصب استفاده می‌کند؛ اگر مرورگر prompt را ارائه نکند، دستور افزودن به صفحهٔ اصلی نمایش داده می‌شود.
- در iPhone/iPad، صفحه را در Safari باز کن، Share را بزن و **Add to Home Screen** را انتخاب کن؛ iOS لزوماً رویداد `beforeinstallprompt` را ارائه نمی‌کند.
- برای آماده‌سازی Android: متغیر `MEDAR_OPS_API_BASE_URL` را روی مبدأ عملیاتی بگذار و اجرا کن: `npm run mobile:android:prepare`.
- برای همگام‌سازی پروژهٔ iOS: `npm run mobile:ios:prepare`. بستهٔ نهایی iOS برای امضا/توزیع، به محیط macOS و مراحل انتشار اپل نیاز دارد.
- `appId` فعلی Capacitor یعنی `com.simorgh.networkoperations` عمداً حفظ شده است. پس از توزیع نسخهٔ نصب‌شده، تغییر آن باعث می‌شود Android/iOS اپ را برنامه‌ای دیگر در نظر بگیرند؛ نام بسته را بدون برنامهٔ مهاجرت عوض نکن.

## انتقال دیتابیس به میزبان PostgreSQL دیگر

ساختار داده با PostgreSQL و فایل‌های مهاجرت نسخه‌بندی شده است؛ با این حال **تعویض `DATABASE_URL` به‌تنهایی تضمین‌شده نیست**، چون Worker فعلی از `@neondatabase/serverless` استفاده می‌کند. اگر مقصد، PostgreSQL عمومی روی هاست دیگری باشد، قبل از جابه‌جایی باید لایهٔ اتصال Worker به درایور پشتیبانی‌شدهٔ آن مقصد (برای نمونه اتصال از طریق Cloudflare Hyperdrive) منتقل و روی یک دیتابیس آزمایشی تست شود. این مرحله نباید روی دیتابیس تولیدی با حدس انجام شود.

فرآیند امن انتقال:

1. یک دیتابیس مقصد **خالی و جداگانه** با نسخهٔ PostgreSQL سازگار آماده کن.
2. در یک محیط امن، از دیتابیس مبدأ backup فرمت custom بگیر؛ رمز اتصال را در تاریخچهٔ شل یا مخزن ثبت نکن:
   ```bash
   pg_dump --format=custom --no-owner --no-acl --file=medar-backup.dump "$SOURCE_DATABASE_URL"
   pg_restore --list medar-backup.dump > medar-backup-contents.txt
   ```
3. فایل را امن منتقل کن و روی دیتابیس خالی مقصد بازگردان:
   ```bash
   pg_restore --exit-on-error --no-owner --no-acl --dbname="$TARGET_DATABASE_URL" medar-backup.dump
   ```
4. شمارش رکوردها، عضویت‌ها، حساب‌ها، شماره‌های مهاجرت و فایل‌های خصوصی را بین مبدأ و مقصد مقایسه کن. خروجی `pg_restore --list` به‌تنهایی کامل بودن داده را اثبات نمی‌کند.
5. با Worker آزمایشی و حساب‌های آزمایشی، ورود، ساخت حساب عضو، بارگیری عضوها، ذخیرهٔ یک رکورد عملیاتی، مجوزهای شرکت و خروج را تست کن. سپس مقصد جدید را در secret سمت سرور تنظیم کن و فقط پس از تأیید، ترافیک را منتقل کن.
6. مبدأ قبلی را تا تأیید پشتیبان و برگشت‌پذیری تغییرات حفظ کن؛ آن را در فرآیند جابه‌جایی پاک نکن.

Backup دیتابیس لزوماً فایل‌هایی را که در فضای شیء خارجی (در صورت پیکربندی) ذخیره شده‌اند شامل نمی‌شود؛ محل فایل‌ها را قبل از cutover بررسی کن. فایل dump حاوی اطلاعات حساس است و باید رمزگذاری و با دسترسی محدود نگهداری شود.

## دروازهٔ آماده‌بودن برای بهره‌برداری

- [ ] مبدأ نهایی HTTPS و fallback مسیرهای اپ تأیید شده است.
- [ ] Worker با دیتابیس موردنظر پاسخ سلامت موفق می‌دهد.
- [ ] ساخت حساب از نشست مالک، ورود با همان نام کاربری/رمز، نمایش عضویت و غیرفعال‌سازی در آزمون واقعی تأیید شده است.
- [ ] تأمین‌کننده فقط پرونده‌های مرتبط خودش و راننده فقط محموله‌های تخصیص‌یافته را می‌بیند.
- [ ] آزمون‌های PostgreSQL، CI مرورگر و بررسی زندهٔ CSS/API موفق‌اند.
- [ ] backup/restore روی دیتابیس جداگانه با شمارش رکوردها اعتبارسنجی شده است.
- [ ] نصب PWA در Android و iOS روی دستگاه واقعی آزموده شده است.

آزمون شبیه‌سازی ۱۰۰ هویت و مجوز در CI از حساب‌ها و داده‌های ساختگی استفاده می‌کند و در پایان تراکنش را rollback می‌کند؛ این آزمون جایگزین آزمون ورود واقعی با نشست مالک یا آزمون دستگاه فیزیکی نیست.
